[![hexlet-check](https://github.com/alexander-lis/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/alexander-lis/ai-for-developers-project-387/actions/workflows/hexlet-check.yml)

**Приложение:** https://calendar-calls-387.onrender.com

Бесплатный план Render усыпляет сервис через 15 минут без запросов: первый запрос будит его примерно за минуту. Если адрес не открывается, приложение запускается локально одной из команд ниже, нужен только Docker:

```bash
git clone https://github.com/alexander-lis/ai-for-developers-project-387.git
cd ai-for-developers-project-387
docker build -t calendar .
docker run --rm -e PORT=8080 -p 8080:8080 calendar
# приложение на http://localhost:8080
```

Для разработки с горячей перезагрузкой нужен [mise](https://mise.jdx.dev): `mise run setup`, затем `mise run dev`, приложение на http://localhost:5173. Остальные команды в [AGENTS.md](AGENTS.md).

## О продукте

Сервис, позволяющий **владельцу** настроить **типы встреч** и дать ссылку **гостям** на свой **календарь**, чтобы они могли забивать свободные **слоты** этими **типами встреч**.

### Основной сценарий
- **Владелец** имеет два интерфейса:
  - UI настройка **типов встреч**, где у каждой есть:
    - Название.
    - Описание.
    - Продолжительность в минутах.
  - UI занятых **слотов** списком с выводом отсортированных информационных блоков о:
    - **Типе встречи**
    - **Имени гостя**.
    - **Продолжительности**.

- **Гость** имеет два интерфейса:
    - UI записи, где можно:
      - В левом блоке выбрать **тип встречи**.
      - В среднем блоке увидеть **календарь** с днями и выбрать день, при этом доступными для выбора будут такие дни, которые:
        - Отстоят от сегодняшнего дня на ближайшие 14 дней вперед.
        - Имеют подходящий оставшийся временной **слот** для выбранного типа встречи.
      - В правом блоке после выбора дня увидеть все свободные временные **слоты**, подходящие для данного **типа встречи**, то есть ее продолжительности и выбрать его.
      - Нажать кнопку «записаться» и во всплывающей модалке ввести имя и нажать кнопку «подтвердить» или «отмена».
    - UI предстоящих встреч, где без выбора гостя видны все предстоящие встречи всех **гостей**, отсортированные, в виде информационных блоков о:
      - **Типе встречи**
      - **Имени гостя**.
      - **Продолжительности**.

### Ограничения
- **Владелец** и **календарь** в системе один, **гостей** в системе сколько угодно.
- **Владелец** - это пользователь, нажавший кнопку «войти как владелец» - это просто тоггл на фронте, так как проект является прототипом. 
- **Гость** - это пользователь, не нажимавший это кнопку или нажавший кнопку «выйти».
- **Гость** идентифицируется вводом имени каждый раз при занимании слота.
- **Слоты**, занятые другими встречами, недоступны для занятия другими встречами.
- **Слоты** на UI нельзя смещать, они заранее нарезаются начиная с 09:00 с шагом, равным продолжительности выбранного **типа встречи**. Свободные **слоты** считает сервер, фронт их только показывает.
- **Календарь** живёт в одном часовом поясе, Europe/Moscow: рабочие часы 09:00–18:00 по будням, время на UI показывается в этом поясе. Записаться можно на сегодня и 13 дней вперёд, но только на **слот**, который ещё не начался.

## Деплой
**Публичная ссылка:** https://calendar-calls-387.onrender.com

Приложение выкатывается одним Docker-образом на Render. Сервер отдаёт и фронтенд, и API с порта из переменной окружения `PORT`, без неё с порта 8080:

```bash
docker build -t calendar .
docker run --rm -e PORT=8080 -p 8080:8080 calendar
```

### Хранение данных
**Данные сбрасываются.** База SQLite лежит в файле внутри контейнера, а у бесплатного плана Render нет постоянного диска, поэтому **типы встреч** и встречи пропадают при каждом редеплое, перезапуске и засыпании сервиса. Сервис засыпает через 15 минут без запросов, первый запрос после этого будит его примерно за минуту и попадает в пустую базу: **владельцу** нужно заново создать **типы встреч**. Для прототипа это осознанное ограничение.

### Подключение Render MCP
Через MCP-сервер Render агент создаёт сервис, запускает деплой и читает логи. Настройка лежит в `.mcp.json` (проектный файл Claude Code), ключей в ней нет: вход идёт через OAuth, а токен Claude Code хранит вне репозитория. `clientId` в файле это публичное имя приложения, не секрет.

1. Запустите `claude` в корне репозитория и разрешите сервер `render` из `.mcp.json`.
2. Наберите `/mcp`, выберите `render`, затем Authenticate, и подтвердите доступ к аккаунту Render в браузере.
3. Попросите агента выбрать рабочее пространство Render.

Сервис `calendar-calls-387` создан из этого репозитория с такими настройками: тип web service, runtime Docker, план free, регион Frankfurt, ветка `master`. `PORT` задаёт сам Render.

**Новая версия выкатывается вручную:** сервис создан по публичному URL репозитория, а автоматический деплой Render требует подключённого GitHub-аккаунта. После влития в `master` попросите агента запустить деплой через MCP или нажмите Manual Deploy в панели Render.

### Проверка выката
Браузерный сценарий гостя и **владельца**, включая отказ повторной записи, запускается по публичной ссылке из `frontend/`. Он оставляет в базе свой **тип встречи** и две встречи.

```bash
E2E_BASE_URL=<публичная ссылка> npx playwright test
```

## Агент в GitHub

Агент [OpenCode](https://opencode.ai/docs/github/) работает в GitHub Actions: обсуждает issue, готовит спецификации и тикеты, правит PR. Воркфлоу [`opencode.yml`](.github/workflows/opencode.yml).

| | |
|---|---|
| Событие | комментарий в issue или PR (`issue_comment`) и комментарий к строке diff (`pull_request_review_comment`), только `types: [created]` |
| Команда | `/oc` или `/opencode` отдельным словом: в начале комментария или после пробела, и затем пробел. Это набор `mentions` по умолчанию, в воркфлоу он записан явно. Ссылка вида `github.com/octocat` или слово `/ocean` командой не считаются и бюджет не тратят |
| Кто может звать | `OWNER`, `MEMBER` или `COLLABORATOR`; комментарии ботов пропускаются. OpenCode дополнительно требует права write у автора |
| Модель | `openrouter/anthropic/claude-haiku-5.5`: Claude Haiku 5.5 через OpenRouter, дешёвая модель с надёжным вызовом инструментов. Ключ в секрете `OPENROUTER_API_KEY`, модель меняется параметром `model` шага Run OpenCode |
| Результат | ответ комментарием от `opencode-agent` в том же issue или PR, правки отдельной веткой и PR (коммиты по Conventional Commits агент делает сам, это правило в `AGENTS.md`; PR агента вливаем squash); прогон и лог во вкладке [Actions](https://github.com/alexander-lis/ai-for-developers-project-387/actions/workflows/opencode.yml) |

Вопросы и решения остаются в комментариях, следующий вызов читает их перед работой.

Скиллы вызываются по имени в комментарии с `/oc`:

- `/oc разбери обращение по скиллу triage, предложи следующий шаг, код пока не меняй`: разбор входящего обращения. Агент проверяет, что уже умеет приложение, ставит метки категории и состояния из `docs/agents/triage-labels.md` и задаёт вопросы о недостающих условиях. Ответы пишутся комментариями в том же issue, следующий `/oc` их читает.
- `/oc запусти скилл to-spec по обсуждению этого issue`: превращает обсуждение в спецификацию и заводит её новым issue в этом репозитории с меткой `ready-for-agent`. Интервью агент не проводит, опирается на уже написанное в ветке.
- `/oc запусти скилл to-tickets по спецификации #N`: разбивает спецификацию на тикеты-вертикальные срезы с блокирующими связями. Каждый тикет становится отдельным issue, в порядке зависимостей. Номера `#N` в комментарии указываются вручную.
- `/oc запусти скилл implement-spec для #N`: реализует спецификацию и тикеты в коде. Результат появляется в PR, который агент открывает из своей ветки; ответ с ссылкой на PR приходит комментарием в issue.

**Что агент знает о проекте.** На раннере он читает репозиторий так же, как локальный агент:

- `AGENTS.md`: команды, правила коммитов и устройство проекта, в том числе команда всех проверок `mise run check`.
- `docs/agents/`: трекер задач (GitHub Issues этого репозитория, работа через `gh`), метки триажа и расположение `GLOSSARY.md` и `docs/adr/`.

Пример ответа агента на такой вопрос есть в [#6](https://github.com/alexander-lis/ai-for-developers-project-387/issues/6): там он называет трекер, проверяет наличие трёх скиллов и отвечает командой `mise run check`.

**Публикация сессий отключена.** Параметр `share` в воркфлоу не задан: текущий action OpenCode его игнорирует, публикация сессий у OpenCode прекращена. Сессии остаются только в логе прогона.

**Отличие от локального агента.** Локально работает Claude Code, скиллы `triage`, `to-spec`, `to-tickets`, `implement-spec`, `tdd`, `code-review` и вызываемые из `triage` `grilling` и `domain-modeling` он берёт из глобального плагина `mattpocock-skills`. На раннере их нет, поэтому воркфлоу скачивает те же скиллы из [mattpocock/skills](https://github.com/mattpocock/skills) на зафиксированном коммите в `~/.config/opencode/skills`. Правила `AGENTS.md` и настройки трекера в `docs/agents/` приходят вместе с кодом.

**Права.** Агент действует от имени GitHub App [opencode-agent](https://github.com/apps/opencode-agent), установленного на репозиторий: токен App выдаётся через OIDC (`id-token: write`), checkout только читает код (`contents: read`, `persist-credentials: false`). `gh` в shell агента получает `GITHUB_TOKEN` с `issues: write`, его используют скиллы, создающие issues и метки, и `pull-requests: read` для чтения PR. Задание `budget` получает `actions: read` для истории прогонов и `pull-requests: read` для проверки форка и head SHA, задание `report` пишет комментарий с `issues: write` и `pull-requests: write`.

**Форки.** Комментарии авторов без доступа к репозиторию до агента не доходят. Если доверенный участник позовёт агента в PR из форка, прогон остановится в задании `budget`, до checkout: агент запускал бы чужой код с ключом модели в окружении. `pull_request_target` не используется.

**Без запросов разрешений.** В CI на вопрос OpenCode «можно ли?» ответить некому, и прогон висел бы до тайм-аута. Поэтому в обоих воркфлоу переменная `OPENCODE_PERMISSION` запрещает доступ вне репозитория (кроме каталога скиллов и временного каталога OpenCode) и повтор одного и того же вызова (`doom_loop`). Неверный путь даёт агенту ошибку, и он продолжает работу.

**Окружение.** Перед вызовом модели воркфлоу ставит те же инструменты, что CI (`mise`, зависимости, Chromium для Playwright), поэтому агент сам запускает `mise run check` и тесты.

**Ограничения.** Вызов агента ограничен 45 минутами, всё задание 55 минутами. На один issue или PR одновременно идёт один прогон, следующая команда ждёт. Остановить прогон: Cancel workflow в Actions; отключить вызовы: Disable workflow; при утечке отозвать ключ в кабинете OpenRouter. Там же задаётся лимит расходов на ключ.

### Предел запусков агента на PR

На один PR агент запускается не больше **3 раз**. Бюджет проверяет задание `budget` в [`opencode.yml`](.github/workflows/opencode.yml) до вызова модели, в задании без ключа.

- **Что считается.** Каждая допущенная команда `/oc` в этом PR: и в общем обсуждении, и на строке diff. Отменённый прогон, прогон, упавший по тайм-ауту, и каждый Re-run (`run_attempt`) тоже расходуют попытку. Новый PR получает новый бюджет; в issue предела нет, он ограничивает именно цикл правок PR.
- **Где хранится счётчик.** В истории Actions этого воркфлоу: допущенная команда получает имя прогона `opencode PR #<номер>` (`run-name`), бюджет это сумма `run_attempt` таких прогонов, кроме пропущенных целиком. Переписать историю может только токен с `actions: write`: у App агента `actions: read`, у `GITHUB_TOKEN` в воркфлоу тоже только чтение. Комментарии в PR служат отчётом и на счётчик не влияют. Ограничение держится, пока история прогонов цела и конфигурация воркфлоу не менялась: администратор репозитория может изменить и то, и другое.
- **Итог без модели.** Задание `report` публикует комментарий «Агент: нужен человек» с причиной, последним SHA PR и ссылкой на логи прогона, если агент не закончил работу:

| Причина | Когда |
|---|---|
| `limit_exhausted` | бюджет PR исчерпан, модель не вызывалась |
| `timeout` | вызов агента превысил свои 45 минут |
| `infra` | не прошла подготовка: checkout, `mise`, зависимости, скиллы, нет секрета `OPENROUTER_API_KEY`, либо PR из форка |
| `agent_failed` | агент завершился ошибкой, в том числе ошибкой модели или OpenRouter |
| `cancelled` | прогон отменили вручную |
| `unknown` | задание остановлено без классификации, причину смотреть в логах |

Следующее действие после такого комментария выбирает человек: доработать ветку вручную, пересмотреть подход или закрыть PR. Автоматического цикла исправлений нет.

### Автотриаж новых обращений

Воркфлоу [`opencode-triage.yml`](.github/workflows/opencode-triage.yml) делает предварительный разбор каждого нового issue без команды `/oc`.

| | |
|---|---|
| Событие | `issues`, только `types: [opened]`: правка описания разбор не повторяет |
| Инструкция | у события `issues` нет комментария с командой, поэтому задание агенту записано в параметре `prompt` шага Run OpenCode: разбор по скиллу `triage`, метка категории (`bug` или `enhancement`) и метка состояния `needs-info` или `needs-triage`, ответ с вопросами комментарием. Код, ветки и PR агент не трогает, `ready-for-agent` и закрытие оставляет человеку |
| Кто запускает | автор issue `OWNER`, `MEMBER` или `COLLABORATOR`, не бот; OpenCode дополнительно проверяет права write. Обращения посторонних до ключа модели не доходят, их разбирают вручную через `/oc` |
| Что пропускается | issue, открытые с меткой состояния `ready-for-agent`, `ready-for-human` или `wontfix` из [`docs/agents/triage-labels.md`](docs/agents/triage-labels.md). Так `to-spec` и `to-tickets` открывают спецификации и тикеты: они уже готовы к реализации. Кроме того, их создаёт `gh` агента с `GITHUB_TOKEN`, а такие события новых прогонов не запускают |
| Права | `contents: read` на checkout, `id-token: write` на токен App, `issues: write` для меток. `pull-requests` не нужен: в issue нет чужого кода |
| Ограничения | тайм-аут 15 минут; группа `concurrency` общая с `opencode.yml` (`opencode-<номер issue>`): по одному issue одновременно идёт один прогон, `/oc` во время автотриажа ждёт его конца |

### Путь доработки от обращения до реализации

1. Пользователь описывает потребность в новом issue своими словами. Автотриаж отвечает разбором и вопросами, или его зовут вручную: `/oc разбери обращение по скиллу triage, предложи следующий шаг, код пока не меняй`.
2. Человек отвечает на вопросы и фиксирует решения комментариями в том же issue.
3. `/oc запусти скилл to-spec по обсуждению этого issue`: спецификация новым issue со ссылкой на исходное. Затем `/oc запусти скилл to-tickets по спецификации #N`: тикеты с блокирующими связями.
4. Человек проверяет сценарии, границы тестирования и зависимости тикетов и подтверждает объём комментарием в исходном issue со ссылками на спецификацию и тикеты.
5. `/oc запусти скилл implement-spec для #N`: PR реализации ссылается на этот комментарий согласования. Если поведение или объём меняются по существу, агент не решает сам, а возвращает вопрос в исходный issue.

Каждый следующий запуск агента читает предыдущие результаты по ссылкам, поэтому обсуждение не теряется между сессиями.

### Авторевью PR

Воркфлоу [`opencode-review.yml`](.github/workflows/opencode-review.yml) делает независимое ревью каждого PR. Это отдельный запуск, он не продолжает сессию реализации и не меняет код.

| | |
|---|---|
| Событие | `pull_request`: `opened`, `synchronize`, `reopened`, `ready_for_review`. Черновики не ревьюим |
| Кто получает ревью | ветки этого репозитория от `OWNER`, `MEMBER`, `COLLABORATOR` и от App `opencode-agent[bot]`, который открывает PR агента. Фильтр всех ботов отключил бы ревью PR агента, поэтому App назван явно. PR из форков ключа модели не получают, release-PR пропускаются; `pull_request_target` не используется |
| Что читает | описание PR, исходное обращение, спецификацию, тикеты и комментарий согласования по ссылкам, diff, результаты CI для head SHA и прошлые комментарии PR. Инструкция в [`.github/review-prompt.md`](.github/review-prompt.md), критерии в [`REVIEW.md`](REVIEW.md): воркфлоу вставляет оба файла в запрос из базовой ветки, чтобы PR не ослаблял собственное ревью |
| Модель | `openrouter/anthropic/claude-haiku-5.5` через обычный CLI `opencode run` (`opencode-ai@1.19.5`). `opencode github run` здесь не подходит: он проверяет права отправителя события и для PR от App получает `permission: none` |
| Права | задание `review` с моделью получает токен только на чтение: `contents`, `issues`, `pull-requests`, `actions`, `checks`, `statuses`. `OPENCODE_PERMISSION` запрещает правку файлов, веб и любые команды shell, кроме чтения (`gh pr view/diff/checks`, `gh issue view`, `gh run list/view`, `git diff/log/show`), без команд, запускающих другие (`rg --pre`, `find -exec`). OpenCode сверяет с правилами каждую команду конвейера, списка `&&` и подстановки `$(...)` отдельно. Комментарий публикует задание `publish` без модели, только у него `pull-requests: write`. OIDC не нужен |
| Результат | комментарий «Авторевью для `<sha>`»: сверка со спецификацией, замечания с файлом, строкой, условиями и последствием, статус CI. Если ревью не получилось, комментарий называет причину (`timeout`, `infra`, `agent_failed`, `unknown`) и даёт ссылку на логи |
| Ограничения | тайм-аут вызова 12 минут, задания 15 минут; новый push отменяет устаревшее ревью того же PR (`concurrency`, `cancel-in-progress: true`), и отменённое ревью ничего не публикует |
| Граница доверия | для веток этого репозитория `pull_request` берёт воркфлоу из ветки PR и выдаёт ему секреты. Значит, ключ модели доступен всем, кто может пушить в репозиторий: это владелец и коллабораторы, их и так допускает фильтр авторов. Инструкция ревьюеру и `REVIEW.md` берутся из базовой ветки, а код, `AGENTS.md` и `GLOSSARY.md` модель читает из ветки PR |

Комментарий авторевью сам исправление не запускает. Человек разбирает каждое замечание: подтверждённое передаёт агенту командой `/oc` в PR (общим комментарием или комментарием к строке diff), ошибочное отклоняет ответом с объяснением. После правок агента в той же ветке CI, проверка работающей версии и авторевью запускаются заново и учитывают уже разобранные замечания.

Если авторевью не стартовало на PR агента, проверьте источник токена: PR и push от `GITHUB_TOKEN` новых прогонов не запускают, от токена App запускают. Там же проверьте, не ждёт ли прогон подтверждения человеком во вкладке Checks PR.

### Шаблон PR и критерии ревью

[`.github/pull_request_template.md`](.github/pull_request_template.md) задаёт разделы описания PR: ссылки на обращение, спецификацию, тикеты и согласование, **проверки** (команды, ссылки на прогоны, проверенный SHA), **риск** (что может сломаться, кого затронет, почему выбрана такая глубина проверки) и **откат** (как отменить в Git, чем проверить восстановление, хватит ли отмены кода для данных). Агент заполняет те же разделы в PR реализации.

[`REVIEW.md`](REVIEW.md) хранит критерии ревью календаря и таблицу глубины проверки по риску. Им пользуются и авторевью, и человек перед мержем.

### Проверка работающей версии

Воркфлоу [`pr-verify.yml`](.github/workflows/pr-verify.yml) на каждое изменение PR собирает приложение из точного head SHA (`ref: github.event.pull_request.head.sha`, а не временного merge-коммита), сверяет его с `git rev-parse HEAD` и проходит браузерный сценарий Playwright с записью trace для всех тестов. Секрета модели в нём нет.

Артефакт `e2e-<head sha>` содержит `verification/result.txt` (номер PR, head SHA, фактический SHA checkout, результат, ссылка на прогон), HTML-отчёт и trace каждого теста. Перед мержем человек сверяет SHA артефакта с текущим head PR (`gh pr view <N> --json headRefOid`) и открывает trace: `npx playwright show-trace <trace.zip>` или https://trace.playwright.dev. После нового push старый артефакт остаётся свидетельством прежней версии, поэтому проверка повторяется.

### Мерж и релиз

- В `master` включена защита ветки: мерж PR требует успешных проверок `check` и `docker-image` из CI и `e2e-head` из PR verify. Администратор может обойти защиту, поэтому перед мержем release-PR (его создаёт `GITHUB_TOKEN`, и CI на нём не запускается) статусы сверяются вручную.
- Решение о мерже принимает человек после проверок и разбора замечаний. PR агента вливаем squash: сообщение коммита берётся из заголовка PR, поэтому заголовок перед мержем приводится к Conventional Commits.
- После мержа `feat:`/`fix:` release-please обновляет release-PR. Ему нужен флаг Settings → Actions → General → **Allow GitHub Actions to create and approve pull requests**: без него release-please готовит ветку и падает на создании PR.
