# Критерии ревью «Календаря звонков»

Критерии для ревью PR: независимое авторевью ([`opencode-review.yml`](.github/workflows/opencode-review.yml)) получает этот файл в запросе, человек сверяется с ним перед мержем. Термины из [GLOSSARY.md](GLOSSARY.md), решения из [docs/adr/](docs/adr/).

## Как писать замечание

Каждое замечание содержит:

- **файл и строку**, например `backend/CalendarApi/Program.cs:104`;
- **условия ошибки**: входные данные, состояние базы, порядок запросов или действий в интерфейсе;
- **последствие**: что увидит Гость или Владелец, какие данные испортятся;
- **уверенность**: подтверждено кодом или тестом, либо это предположение.

Если подтверждённых дефектов нет, ревьюер так и пишет. Ошибочные замечания ради количества не нужны. Форматирование, порядок импортов и стиль проверяет линтер в CI (`mise run lint`), его вывод в ревью не повторяем.

## Спецификация и объём

- PR реализации ссылается на исходное обращение, спецификацию, тикеты и комментарий согласования человеком. Если ссылок нет или они не открываются, это пробел, о нём пишем.
- Каждый сценарий и критерий приёмки тикетов либо закрыт кодом и тестом, либо явно назван незакрытым.
- Изменение поведения или объёма сверх согласованного отмечаем отдельно: такие решения принимает человек в исходном issue, а не автор PR.

## Поведение календаря

- **Занятый Слот не доступен для повторной записи.** Слот, который пересекает существующая Встреча, не появляется среди свободных и не принимается `POST /api/meetings`: ответ 409, Встреча не создаётся.
- **Проверка пересечений внутри немедленной транзакции** (ADR 0003). Чтение занятости, вставка Встречи и фиксация идут в одной транзакции. Вынос проверки наружу или второй `SaveChanges` между проверкой и вставкой возвращает гонку двух одновременных записей.
- **Пересечение по интервалам, а не по совпадению Слотов** (ADR 0002). Встреча Типа на 45 минут занимает часть Слота Типа на 30 минут, и такой Слот тоже занят.
- **Только будущие Слоты в Рабочих часах и Окне записи.** Сегодня и 13 дней вперёд по Поясу Календаря (Europe/Moscow), будни, 09:00–18:00. Слот, начало которого уже наступило, не принимается. Время сравнивается в UTC, а показывается в Поясе Календаря независимо от пояса браузера.
- **Снимок Типа встречи** (ADR 0001). Правка или удаление Типа встречи не меняет уже созданные Встречи; списки Встреч не разыменовывают `meetingTypeId`.
- **Неудачная запись не оставляет следов.** При 400, 404 и 409 ничего из запроса (имя Гостя, тема и другие поля Встречи) не сохраняется.
- **Роли на фронте.** Бекенд о ролях не знает. Данные, которые спецификация показывает только Владельцу, не выводятся на страницах Гостя.

## Контракт и данные

- API меняется через `contract/main.tsp` и `mise run generate`; руками правленные `contract/tsp-output/` и `frontend/src/client/` это ошибка. Фронтенд ходит в API только через `@/client`.
- `Program.cs` и тесты бекенда обновлены вместе с контрактом: компилятор их не сверяет, сверяют `response.MatchesContract(path)`.
- Новая колонка приходит миграцией EF Core. Миграция применима к базе с уже существующими Встречами: новое обязательное поле без значения по умолчанию ломает старые строки.
- Правила валидации одинаковы на сервере и в форме: длина, обрезка пробелов, пустое значение.

## Тесты

- Основной и негативный сценарии спецификации покрыты тестами на уровне, который назвала спецификация: API-тесты со сверкой по `openapi.yaml`, юнит- и компонентные тесты фронтенда, браузерный сценарий Playwright.
- Тест проверяет поведение, которое видит пользователь или клиент API, а не внутреннее устройство. Тест, который проходит и без нового кода, ничего не доказывает.
- Существующие тесты не ослаблены и не удалены без объяснения в PR. Параллельный тест на один Слот проходит без изменений.

## Риск и глубина проверки

Глубину проверки выбираем по последствиям ошибки, а не по числу строк:

| Изменение | Что проверить перед мержем |
|---|---|
| Подпись, текст, вёрстка | Соответствие задаче и вид в интерфейсе |
| Новое поле Встречи, валидация | Контракт, миграция на старых данных, сервер и форма по одним правилам, отказ без следов |
| Расчёт свободных Слотов, Конфликт, транзакция | Основной сценарий, пересечения Встреч разных Типов, соседние Слоты, параллельная запись, граница Окна записи |
| Права GitHub Actions, секреты, триггеры воркфлоу | Кому и при каком событии доступны код и секреты, PR из форков, отдельное решение человека |

## Воркфлоу и агенты

- Секрет модели не доступен PR из форков и командам недоверенных авторов; `pull_request_target` с запуском кода из PR не используется.
- Права токенов минимальны и подписаны комментарием «зачем». Модель не получает токен с правом записи там, где пишет отдельный шаг.
- Предел запусков агента на PR проверяется до вызова модели. Счётчик, который не может вернуть 0 (текущий прогон всегда в истории), при 0 отказывает, а не пропускает.
- Значения YAML с ` #` берутся в кавычки: без них YAML отрезает остаток строки как комментарий.
- Коммиты по Conventional Commits; заголовок PR годится как сообщение squash-коммита.
